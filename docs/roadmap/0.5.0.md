# Moro 0.5.0 roadmap

This document records the preliminary scope and design decisions for Moro 0.5.0. It is intended to capture decisions made during planning; implementation-level details may be refined later in dedicated design documents.

## Differential kinematics

### Status

Accepted as a candidate feature for Moro 0.5.0.

### Objective

Provide tools to map velocities between joint space and task space through the robot Jacobian, while keeping the API explicit and suitable for teaching differential kinematics.

The initial scope covers

\[
\dot{x} = J_{\mathrm{task}}(q)\dot{q}
\]

and differential inverse kinematics of the form

\[
\dot{q} \approx J_{\mathrm{task}}^{\dagger}(q)\dot{x}.
\]

### Task-space representation

The canonical geometric-twist ordering is

\[
(v_x, v_y, v_z, \omega_x, \omega_y, \omega_z).
\]

Task-space components are selected explicitly using the names

- `vx`, `vy`, `vz` for linear-velocity components;
- `wx`, `wy`, `wz` for angular-velocity components.

Examples:

```python
task=("vx", "vy")
task=("vx", "vy", "wz")
task=("vz", "wy")
```

The following convenience presets are planned:

- `task="linear"` -> `("vx", "vy", "vz")`
- `task="angular"` -> `("wx", "wy", "wz")`
- `task="twist"` -> all six components in canonical order.

The task space will not be inferred from the length of the requested velocity vector. Explicit component selection is preferred to avoid ambiguity and to preserve the educational character of the API.

Roll, pitch and yaw terminology will not be used for the angular rows of the geometric Jacobian, because these rows represent angular velocity rather than Euler-angle rates.

### Preliminary public API

The module is expected to live in `moro/differential_kinematics.py` and expose three main operations.

```python
task_jacobian(
    robot,
    q=None,
    *,
    task="twist",
    parameters=None,
)
```

Returns the Jacobian associated with the selected task-space components. When no numerical configuration is supplied, this operation should remain useful for symbolic/educational inspection.

```python
cartesian_velocity(
    robot,
    q,
    qd,
    *,
    task="twist",
    parameters=None,
)
```

Computes the selected task-space velocity from joint velocities using

\[
\dot{x}=J_{\mathrm{task}}\dot{q}.
\]

This operation is expected to return the resulting velocity vector directly.

```python
solve_velocity_ik(
    robot,
    q,
    velocity,
    *,
    task="twist",
    method="pinv",
    damping=None,
    joint_velocity_limits=None,
    parameters=None,
)
```

Computes joint velocities that best reproduce a requested task-space velocity.

### Differential IK methods

The initial release scope includes two methods:

- `method="pinv"`: Moore-Penrose pseudoinverse;
- `method="dls"`: damped least squares.

Damped least squares is included to provide more robust behavior near singular configurations and to support direct comparison with the pseudoinverse in teaching examples.

An explicit matrix-inverse method is not planned for the public API. The pseudoinverse already covers the regular square case while remaining applicable to non-square Jacobians.

### `VelocityIKSolution`

`solve_velocity_ik()` will return a structured `VelocityIKSolution` result rather than only the joint-velocity vector.

The preliminary result information includes at least:

- `qd`
- `achieved_velocity`
- `residual`
- `residual_norm`
- `rank`
- `condition_number`
- `method`
- `success`
- `message`

The purpose of the structured result is to expose useful numerical diagnostics, particularly when studying redundancy and behavior near singularities.

The exact semantics and invariants of these fields will be defined during detailed module design. In particular, the precise meaning of `success`, residual conventions, numerical tolerances, rank evaluation, infinite condition numbers, and the effect of velocity saturation remain implementation-level decisions.

### Joint-velocity limits

`solve_velocity_ik()` is planned to accept optional joint-velocity limits through `joint_velocity_limits`.

For the initial scope, simple output saturation is considered sufficient, provided its effect on the achieved task-space velocity is exposed and clearly documented. More advanced constrained least-squares formulations are outside the current scope.

### Symbolic and numerical behavior

Moro should preserve its symbolic-first character where useful.

`task_jacobian()` is expected to support symbolic inspection and numerical evaluation. Operations such as `cartesian_velocity()` and `solve_velocity_ik()` are primarily intended as numerical operations, avoiding general symbolic pseudoinverse calculations that could produce unnecessarily large expressions.

The `parameters` argument should follow the same general philosophy already used by numerical inverse kinematics, allowing symbolic geometric parameters in a robot model to be substituted for numerical evaluation.

### Initial examples and tests

The feature should eventually include examples covering at least:

- differential kinematics of a planar 2R manipulator;
- planar task selection using `("vx", "vy")` and `("vx", "vy", "wz")`;
- a redundant manipulator solved with the pseudoinverse;
- comparison of pseudoinverse and DLS behavior near a singular configuration;
- revolute and prismatic joints;
- symbolic geometric parameters evaluated numerically.

Tests should cover task selection, dimensional validation, numerical evaluation, both differential-IK methods, singular and near-singular cases, velocity-limit handling, and result-object consistency.

### Explicitly outside the initial 0.5.0 scope

The following capabilities are not part of the accepted initial differential-kinematics scope:

- null-space optimization;
- secondary-task optimization;
- obstacle avoidance;
- gradient-based joint-limit avoidance;
- resolved-rate controllers and complete trajectory integration;
- motion planning;
- differential acceleration kinematics;
- Jacobian time derivative `Jdot`;
- dynamic control.

These capabilities may be considered in later versions once the velocity-level API is stable.

### Deferred detailed-design decisions

The following points are intentionally deferred until the detailed design and implementation phase of `differential_kinematics.py`:

- exact validation rules and exception messages;
- numerical tolerances;
- precise `VelocityIKSolution` invariants;
- semantics of `success`;
- residual sign and interpretation;
- rank and condition-number computation policy;
- exact treatment of `damping` when another method is selected;
- interaction between joint-velocity saturation and diagnostic fields;
- detailed internal helpers and caching strategy.

## Workspace

### Status

Accepted as a candidate feature for Moro 0.5.0.

### Objective

Provide a simple and general way to approximate the reachable workspace of a serial manipulator by sampling valid joint configurations and evaluating the corresponding end-effector positions.

The initial scope is limited to the sampled reachable workspace of the end effector under finite joint limits. It does not attempt to compute an exact analytical boundary or a dextrous workspace.

Conceptually, the workspace is

\[
\mathcal{W} = \left\{ \mathbf{p}(\mathbf{q}) \mid \mathbf{q} \in \mathcal{Q} \right\},
\]

where \(\mathcal{Q}\) is the joint-space domain defined by the selected joint limits.

### Sampling strategy

The initial implementation will use uniform random sampling in joint space.

For each sample,

\[
q_i \sim [q_{i,\min}, q_{i,\max}],
\]

and the end-effector position is evaluated using forward kinematics.

Only random sampling is planned for the initial 0.5.0 scope. Grid-based sampling is intentionally deferred because its computational cost grows exponentially with the number of joints.

A `seed` argument will be supported to make sampling reproducible in examples, tests, and comparisons.

### Preliminary public API

The implementation is expected to live in `moro/workspace.py` and expose a main sampling operation together with a structured result object.

```python
sample_workspace(
    robot,
    *,
    samples=1000,
    joint_limits=None,
    parameters=None,
    seed=None,
)
```

The function samples valid joint configurations and returns a `Workspace` object containing the resulting Cartesian points and the corresponding joint configurations.

Example:

```python
ws = sample_workspace(
    robot,
    samples=5000,
    parameters={l1: 1.0, l2: 0.8},
    seed=42,
)
```

When `joint_limits` is not provided explicitly, the function should use the limits associated with the robot model.

### `Workspace` result object

The preliminary result object will represent sampled workspace data rather than the output of an iterative solver.

It is expected to expose at least:

- `points`
- `configurations`
- `joint_limits`
- `samples`
- `bounds`

`points` should store Cartesian end-effector positions as an `N x 3` numerical array, even for planar manipulators.

`configurations` should store the corresponding joint-space samples. Retaining this association is considered important because it enables later analyses such as manipulability, singularity classification, and other configuration-dependent metrics without resampling the workspace.

`bounds` may expose axis-aligned Cartesian limits such as

```python
(
    (xmin, xmax),
    (ymin, ymax),
    (zmin, zmax),
)
```

without implying an exact reconstruction of the workspace boundary.

### Joint limits

Finite joint limits are required for workspace sampling.

If any joint has an unbounded sampling interval and no finite override is supplied through `joint_limits`, `sample_workspace()` should fail with a clear validation error.

This behavior is intentional: a sampled workspace is only meaningful relative to a finite joint-space domain.

The feature should support revolute, prismatic, and mixed-joint manipulators.

### Symbolic and numerical behavior

Moro should preserve symbolic robot definitions while evaluating the workspace numerically.

The `parameters` argument should allow symbolic geometric parameters to be assigned numerical values before sampling, following the same general evaluation philosophy used by other numerical modules.

If unresolved symbols remain in the end-effector position after applying joint values and provided parameters, the operation should fail with a clear error rather than silently returning symbolic samples.

For performance, repeated symbolic substitution for every sample should be avoided where possible. A numerical callable derived from the symbolic forward-kinematics expression, for example through `sympy.lambdify`, is the expected implementation direction.

### Visualization

Workspace visualization is considered part of the feature, but plotting responsibilities should remain in the visualization subsystem rather than being embedded directly in the `Workspace` data object.

The exact public visualization entry point is deferred until detailed design. Possible forms include integration with `RobotVisualizer` or a dedicated workspace-plotting helper.

Internally, workspace data should always retain three Cartesian coordinates. Planar workspaces may be displayed in 2D when appropriate, but the underlying representation should remain consistent with spatial robots.

### Initial examples and tests

The feature should eventually include examples covering at least:

- reachable workspace of a planar 2R manipulator;
- sampled workspace of a spatial manipulator;
- revolute and prismatic joints;
- explicit and model-defined joint limits;
- symbolic geometric parameters evaluated numerically;
- reproducible sampling with `seed`;
- workspace visualization.

Tests should cover finite-limit validation, sampling reproducibility, output shapes, consistency between Cartesian points and stored configurations, revolute/prismatic support, symbolic-parameter substitution, and invalid-input handling.

### Explicitly outside the initial 0.5.0 scope

The following capabilities are not part of the accepted initial workspace scope:

- analytical workspace computation;
- exact boundary reconstruction;
- grid-based sampling;
- adaptive sampling;
- workspace area or volume estimation;
- convex hull as a representation of the workspace;
- dextrous workspace;
- orientation or pose workspace;
- constant-orientation workspace;
- obstacle-aware workspace;
- collision checking;
- manipulability maps;
- singularity maps;
- sampling arbitrary points on intermediate links.

These capabilities may be considered in future versions once the sampled workspace representation and API are stable.

### Deferred detailed-design decisions

The following points are intentionally deferred until the detailed design and implementation phase of `workspace.py`:

- exact `Workspace` dataclass fields and invariants;
- validation rules and exception messages;
- precise handling and precedence of robot-defined versus explicitly supplied joint limits;
- numerical array types and shape conventions beyond the agreed `N x 3` Cartesian representation;
- internal sampling helpers;
- exact numerical evaluation and caching strategy;
- visualization API and backend integration;
- thresholds for recognizing or displaying planar workspaces.

## Direct dynamics and numerical simulation

### Status

Accepted as a candidate feature for Moro 0.5.0.

### Objective

Extend Moro from symbolic dynamic-model construction to numerical evaluation and time-domain simulation of serial manipulators.

The symbolic robot model remains responsible for exposing quantities such as

\[
M(q), \qquad C(q,\dot q), \qquad G(q),
\]

while the new `moro.dynamics` module will provide numerical operations based on the standard robot dynamic model

\[
M(q)\ddot q + C(q,\dot q)\dot q + G(q) = \tau.
\]

The intended separation is:

- `Robot`: symbolic model construction and inspection;
- `moro.dynamics`: numerical inverse/forward dynamics and time integration.

### Symbolic dynamics API on `Robot`

The symbolic dynamics capabilities currently exposed by `Robot` should remain methods of the robot model. In particular, the following interfaces remain conceptually associated with `Robot`:

- `inertia_matrix()`;
- `coriolis_matrix()`;
- `gravity_vector()`;
- energy and Lagrangian calculations.

For Moro 0.5.0, the two existing dynamic-model names should be revised for clarity:

```text
dynamic_model()             -> euler_lagrange_equations()
dynamic_model_matrix_form() -> dynamic_model()
```

`euler_lagrange_equations()` will expose the symbolic Euler-Lagrange equations

\[
\frac{d}{dt}\left(\frac{\partial L}{\partial \dot q_i}\right)
-\frac{\partial L}{\partial q_i}
= \tau_i,
\]

while `dynamic_model()` will expose the standard symbolic matrix form

\[
M(q)\ddot q + C(q,\dot q)\dot q + G(q) = \tau.
\]

The term *manipulator equation* may be used in the theory and documentation for this standard form, while `dynamic_model()` is preferred as the public API name because it is more immediately understandable and explicitly identifies the result as a dynamic model.

The exact backward-compatibility policy for the old names is deferred to detailed design. A temporary deprecation period is preferred unless there is a strong reason for an immediate pre-1.0 breaking change.

### Preliminary public API

The numerical implementation is expected to live in `moro/dynamics.py` and expose at least:

```python
inverse_dynamics(
    robot,
    q,
    qd,
    qdd,
    *,
    parameters=None,
)
```

```python
forward_dynamics(
    robot,
    q,
    qd,
    tau,
    *,
    parameters=None,
)
```

```python
state_derivative(
    robot,
    t,
    state,
    tau=None,
    *,
    parameters=None,
)
```

```python
simulate(
    robot,
    t_span,
    q0,
    qd0=None,
    *,
    tau=None,
    parameters=None,
    t_eval=None,
    method="RK45",
    rtol=None,
    atol=None,
    max_step=None,
)
```

The exact defaults and accepted solver options remain subject to detailed design.

### Inverse dynamics

`inverse_dynamics()` evaluates the required generalized joint forces or torques for a specified joint configuration, velocity, and acceleration:

\[
\tau = M(q)\ddot q + C(q,\dot q)\dot q + G(q).
\]

This operation is numerical and should return the resulting generalized-force vector directly.

Including inverse dynamics together with forward dynamics provides a symmetric numerical API:

```python
tau = inverse_dynamics(robot, q, qd, qdd, parameters=params)
qdd = forward_dynamics(robot, q, qd, tau, parameters=params)
```

### Forward dynamics

`forward_dynamics()` evaluates joint accelerations for a specified state and generalized-force input:

\[
\ddot q = M(q)^{-1}
\left[\tau - C(q,\dot q)\dot q - G(q)\right].
\]

The implementation should solve the linear system numerically rather than explicitly forming the matrix inverse.

`forward_dynamics()` is a pointwise numerical operation and should return the acceleration vector directly rather than a structured result object.

### First-order state derivative

`state_derivative()` will be a public numerical operation.

For the state

\[
y =
\begin{bmatrix}
q\\
\dot q
\end{bmatrix},
\]

it evaluates

\[
\dot y =
\begin{bmatrix}
\dot q\\
\ddot q
\end{bmatrix}.
\]

Its primary implementation role is to provide the first-order vector field required by an ODE integrator. Its public educational role is to make explicit the transformation from the second-order robot equations of motion to the first-order state-space form used for numerical integration.

`state_derivative()` is not intended to construct a symbolic state-space model in the initial 0.5.0 scope.

### Generalized-force input `tau`

The numerical API will distinguish pointwise dynamics from time-domain simulation.

`inverse_dynamics()` and `forward_dynamics()` accept numerical generalized-force/acceleration vectors for a single state evaluation.

`state_derivative()` and `simulate()` should accept `tau` in the following forms:

- `None`, interpreted as zero generalized force;
- a constant numerical vector;
- a callable with signature conceptually equivalent to

```python
tau(t, q, qd)
```

that returns the generalized-force vector at the current time and state.

Allowing a callable provides sufficient flexibility for time-varying inputs and simple user-defined feedback laws without introducing a dedicated controller framework in 0.5.0.

### Numerical simulation

`simulate()` integrates the first-order dynamic system over a requested time interval.

`q0` is required. If `qd0` is omitted, zero initial joint velocities are assumed.

`t_span` defines the integration interval, while optional `t_eval` values allow users to request output at specific times. This is especially useful for plotting, animation, reproducible examples, and comparison of simulations.

The initial integration backend will use `scipy.integrate.solve_ivp`.

SciPy will become a required Moro dependency in 0.5.0. This is considered a natural extension of the scientific Python stack used by Moro and avoids optional-dependency complexity for a feature intended to be part of the main library.

### `DynamicsSolution`

`simulate()` should return a structured `DynamicsSolution` object rather than the raw SciPy result.

The preliminary result information includes at least:

- `t`;
- `q`;
- `qd`;
- `qdd`;
- `success`;
- `message`.

The preferred public array orientation is:

```python
solution.t.shape   == (N,)
solution.q.shape   == (N, dof)
solution.qd.shape  == (N, dof)
solution.qdd.shape == (N, dof)
```

so that `solution.q[k]` directly represents the joint configuration at sample `k`.

`qdd` may be reconstructed by evaluating the forward-dynamics model at the returned states rather than being stored directly by the underlying ODE solver.

The exact result-object invariants and whether additional solver metadata should be exposed are deferred to detailed design.

### Symbolic parameters and numerical compilation

The numerical dynamics functions should support robot models containing symbolic geometric and physical parameters through the `parameters` argument.

Repeated symbolic substitution during ODE integration should be avoided. The intended implementation direction is to construct the symbolic dynamic quantities once, substitute fixed parameters, and create reusable numerical callables, for example using `sympy.lambdify`.

Conceptually:

```text
Robot symbolic model
        ↓
M(q), C(q, qd), G(q)
        ↓
parameter substitution / numerical compilation
        ↓
fast numerical callables
        ↓
forward dynamics / ODE integration
```

The exact caching and compilation strategy is intentionally deferred to detailed design.

### Relationship with visualization

The dynamics module should not depend directly on the visualization subsystem.

The chosen result-array convention should nevertheless make simulation results easy to animate, for example conceptually:

```python
solution = simulate(...)
visualizer.animate(solution.q)
```

Whether `RobotVisualizer` should later accept a `DynamicsSolution` object directly is a separate visualization-design decision.

### Joint limits

Joint limits will not be physically enforced by the initial forward-dynamics simulator.

Simply clipping positions or velocities at a joint limit would not constitute a physically correct model of stops, impacts, or constrained dynamics. Therefore, the initial simulator should integrate the unconstrained dynamic model and document this behavior explicitly.

Physical stops, impacts, constrained motion, and event-based joint-limit handling are outside the initial scope.

### Initial examples and tests

The feature should eventually include examples covering at least:

- inverse-dynamics evaluation for a simple manipulator;
- forward-dynamics evaluation from a known torque input;
- consistency between inverse and forward dynamics;
- free motion under gravity;
- constant applied torque;
- time-varying torque through a callable;
- a simple user-defined PD-like feedback law implemented as a `tau(t, q, qd)` callable;
- numerical simulation of a planar 2R manipulator;
- use of simulation output with visualization;
- symbolic physical parameters evaluated numerically.

Tests should cover numerical dimensions and validation, revolute/prismatic support, symbolic-parameter substitution, inverse/forward consistency, zero-input behavior, callable torque inputs, state-vector construction, integration success/failure handling, requested `t_eval` output, and `DynamicsSolution` consistency.

### Explicitly outside the initial 0.5.0 scope

The following capabilities are not part of the accepted initial direct-dynamics and simulation scope:

- symbolic state-space-model construction;
- friction models;
- external Cartesian forces or wrenches;
- contact dynamics;
- collision response;
- impact dynamics;
- physical enforcement of joint limits;
- actuator models;
- torque saturation;
- dedicated controller classes;
- computed-torque control as a built-in controller;
- constrained or closed-chain dynamics;
- advanced event handling;
- multibody contact simulation.

Users may still express simple feedback laws directly through the callable `tau(t, q, qd)` interface.

### Deferred detailed-design decisions

The following points are intentionally deferred until the detailed design and implementation phase of `dynamics.py`:

- exact validation rules and exception messages;
- backward-compatibility/deprecation policy for `dynamic_model()` and `dynamic_model_matrix_form()`;
- exact `DynamicsSolution` dataclass fields and invariants;
- numerical array types and accepted input shapes;
- default ODE tolerances and exposed solver options;
- exact handling of failed integrations;
- policy for unresolved symbolic parameters;
- internal numerical compilation and caching strategy;
- whether numerical callables should be cached on the robot or managed entirely inside `dynamics.py`;
- exact reconstruction policy for `qdd`;
- detailed visualization interoperability.

## Singularities and manipulability

### Status

Accepted as a candidate feature for Moro 0.5.0.

### Objective

Provide numerical tools for analyzing local kinematic capability through the task Jacobian, with particular emphasis on singular configurations, conditioning, and velocity manipulability.

The feature should reuse the same task-space conventions defined for differential kinematics so that singularity and manipulability analysis are always interpreted with respect to an explicit kinematic task.

### Task-space representation

All analysis functions should operate on the same task components and presets already defined for `task_jacobian()`:

- `task="linear"`;
- `task="angular"`;
- `task="twist"`;
- explicit tuples such as `("vx", "vy")` or `("vx", "vy", "wz")`.

This is important because singularity is task dependent. A configuration may be singular for a full six-dimensional twist task while remaining nonsingular for a reduced position or planar-motion task.

### Module placement

The initial implementation is expected to remain in `moro/differential_kinematics.py` rather than introducing a separate singularity-analysis module.

This keeps Jacobian-based analysis close to `task_jacobian()`, differential inverse kinematics, and the numerical linear-algebra tools that support them. A separate module may be considered later if the analysis API grows substantially.

### Preliminary public API

The initial analysis API is expected to include:

```python
singular_values(
    robot,
    q,
    *,
    task="twist",
    parameters=None,
)
```

```python
jacobian_rank(
    robot,
    q,
    *,
    task="twist",
    parameters=None,
    tol=None,
)
```

```python
condition_number(
    robot,
    q,
    *,
    task="twist",
    parameters=None,
)
```

```python
is_singular(
    robot,
    q,
    *,
    task="twist",
    parameters=None,
    tol=None,
)
```

```python
manipulability(
    robot,
    q,
    *,
    task,
    parameters=None,
)
```

The exact parameter order, tolerances, and return dtypes remain subject to detailed design.

### Singular-value decomposition

The numerical analysis should be based primarily on the singular-value decomposition of the selected task Jacobian:

\[
J_{\mathrm{task}} = U\Sigma V^T.
\]

Exposing `singular_values()` directly is considered useful for teaching because the singular values provide the common basis for rank estimation, conditioning, and geometric interpretations of local motion capability.

### Jacobian rank

`jacobian_rank()` returns the numerical rank of the selected task Jacobian.

A configuration is considered singular for a selected task when the Jacobian loses rank relative to its maximum possible rank:

\[
\operatorname{rank}(J_{\mathrm{task}}) < \min(m,n),
\]

where \(m\) is the task dimension and \(n\) is the number of joints.

The exact tolerance used to classify singular values as numerically zero is deferred to detailed design. When `tol=None`, the implementation should use a standard scale-aware numerical policy rather than a fixed arbitrary threshold.

### Singularity detection

`is_singular()` should provide the corresponding Boolean diagnostic for the selected task.

Singular configurations are valid inputs to the analysis API and should not normally raise an error merely because rank is lost. The purpose of the function is precisely to diagnose that condition.

### Condition number

`condition_number()` should measure numerical conditioning using the singular values, conceptually:

\[
\kappa(J) = \frac{\sigma_{\max}}{\sigma_{\min}}.
\]

This provides a continuous indicator of proximity to singular behavior, complementing the discrete rank and `is_singular()` diagnostics.

For an effectively singular Jacobian, the expected result is `inf` rather than an exception. Exact tolerance semantics remain a detailed-design decision.

### Manipulability

The initial manipulability metric will be the Yoshikawa velocity-manipulability measure:

\[
w(q) = \sqrt{\det\left(J_{\mathrm{task}}J_{\mathrm{task}}^T\right)}.
\]

`manipulability()` will return a scalar numerical value directly rather than a structured result object.

For tasks with dimension larger than the number of available joints, \(J_{\mathrm{task}}J_{\mathrm{task}}^T\) is necessarily rank deficient and the measure becomes zero. This behavior should be documented rather than hidden by an alternative formula.

### Explicit `task` for manipulability

Unlike the rank, condition-number, and singularity diagnostics, `manipulability()` should require `task` to be specified explicitly in the initial API.

For example:

```python
w_xy = manipulability(
    robot,
    q,
    task=("vx", "vy"),
)
```

or:

```python
w_pos = manipulability(
    robot,
    q,
    task="linear",
)
```

This decision is intentional. Manipulability is a quantitative metric whose numerical value depends strongly on the selected task space, and there is no single task-independent scalar that should silently be presented as "the" manipulability of the robot.

Requiring explicit task selection also avoids silently defaulting to a full twist Jacobian, where linear and angular velocity components have different physical scales and units. Full-twist manipulability remains available through `task="twist"`, but its scale dependence should be documented clearly.

Automatic weighting or normalization between linear and angular components is not planned for the initial 0.5.0 scope.

### Symbolic and numerical behavior

The initial singularity and manipulability API is primarily numerical.

Robot models may retain symbolic geometric parameters, with numerical values supplied through `parameters` during evaluation. The implementation should reuse the same numerical Jacobian-evaluation strategy as differential kinematics where practical.

General symbolic singularity-condition solving is explicitly outside the initial scope because it can require determinant/minor analysis, symbolic rank reasoning, and potentially expensive simplification.

### Relationship with workspace

The initial workspace and manipulability APIs should remain independent.

`sample_workspace()` should not automatically compute manipulability or singularity labels. However, storing the sampled joint configurations allows these metrics to be evaluated later at each workspace sample without changing the workspace data model.

This creates a natural future path toward workspace visualizations colored by manipulability or singularity proximity without coupling the two features prematurely.

### Initial examples and tests

The feature should eventually include examples covering at least:

- rank loss in a planar manipulator;
- singular and nonsingular configurations;
- condition-number growth near a singular configuration;
- singular-value interpretation;
- Yoshikawa manipulability for a planar position task;
- comparison of manipulability at several configurations;
- explicit reduced tasks such as `("vx", "vy")`;
- revolute and prismatic joints;
- symbolic geometric parameters evaluated numerically.

Tests should cover task selection, output types, numerical rank, tolerance behavior, singular/nonsingular classification, condition-number behavior, singular values, Yoshikawa manipulability, dimensionally underactuated tasks, revolute/prismatic support, and symbolic-parameter substitution.

### Explicitly outside the initial 0.5.0 scope

The following capabilities are not part of the accepted initial singularities and manipulability scope:

- symbolic singularity conditions;
- symbolic classification of singularities;
- manipulability ellipsoids and their visualization;
- isotropy indices as separate public metrics;
- manipulability gradients;
- manipulability optimization;
- null-space manipulability maximization;
- automatic workspace manipulability maps;
- automatic workspace singularity maps;
- dynamic manipulability;
- force manipulability;
- automatic weighting between translational and rotational components;
- characteristic-length normalization for full-twist metrics.

These capabilities may be considered once the task-space and numerical analysis APIs are stable.

### Deferred detailed-design decisions

The following points are intentionally deferred until detailed design and implementation:

- exact numerical rank tolerance policy;
- relationship between the tolerance used by `jacobian_rank()` and `is_singular()`;
- exact treatment of very small singular values in `condition_number()`;
- numerical handling of small negative determinant values caused by floating-point roundoff in the Yoshikawa measure;
- validation and exception messages;
- shared internal helpers with `solve_velocity_ik()`;
- caching and numerical Jacobian-evaluation strategy;
- whether `singular_values()` should return all singular values or only the nonzero numerical subset.

## Trajectory generation

### Status

Accepted as a candidate feature for Moro 0.5.0.

### Objective

Provide compact, educational tools for generating time-parameterized point-to-point trajectories in joint space and Cartesian position space.

The initial feature should remain independent of robot-specific inverse kinematics, joint limits, dynamics, and visualization. Trajectory generation defines the desired evolution of coordinates over time; other Moro modules may subsequently consume those trajectories.

The initial scope distinguishes between:

- joint-space trajectories `q(t)`;
- Cartesian position trajectories `p(t)`.

Pose and orientation trajectories are intentionally deferred until the full-pose inverse-kinematics and orientation-representation requirements are defined.

### Module placement

The implementation is expected to live in:

```text
moro/trajectory.py
```

with a small public API centered on trajectory-generation functions and structured result objects.

### Preliminary public API

The initial module is expected to expose:

```python
joint_trajectory(
    q0,
    qf,
    t,
    *,
    method="quintic",
    qd0=None,
    qdf=None,
    qdd0=None,
    qddf=None,
)
```

and:

```python
position_trajectory(
    p0,
    pf,
    t,
    *,
    method="quintic",
    v0=None,
    vf=None,
    a0=None,
    af=None,
)
```

The exact naming of derivative boundary-condition arguments remains subject to detailed design, but the public distinction between joint and Cartesian-position trajectories is accepted preliminarily.

### Supported interpolation methods

The initial 0.5.0 scope should include three methods:

- `method="linear"`;
- `method="cubic"`;
- `method="quintic"`.

Keeping all three methods is intentional for teaching. They provide a natural progression from simple interpolation toward increasingly smooth boundary conditions.

#### Linear interpolation

Linear interpolation provides the simplest point-to-point reference and is useful as a baseline for comparison with polynomial trajectories.

It should depend only on the initial and final coordinates and the supplied time interval. Derivative boundary conditions should not be silently accepted or ignored for the linear method.

Its limitations, particularly velocity discontinuities when connecting the trajectory to rest before and after the commanded interval, should be documented clearly.

#### Cubic interpolation

Cubic interpolation should support initial and final position and velocity constraints.

When the initial or final velocity is omitted, the corresponding value should default to zero.

Conceptually, the trajectory satisfies:

\[
q(t_0)=q_0, \qquad q(t_f)=q_f,
\]

\[
\dot q(t_0)=\dot q_0, \qquad \dot q(t_f)=\dot q_f.
\]

The analogous conditions apply to Cartesian position trajectories.

#### Quintic interpolation

Quintic interpolation should support position, velocity, and acceleration boundary conditions.

Omitted initial/final velocities and accelerations should default to zero.

Conceptually:

\[
q(t_0)=q_0, \qquad q(t_f)=q_f,
\]

\[
\dot q(t_0)=\dot q_0, \qquad \dot q(t_f)=\dot q_f,
\]

\[
\ddot q(t_0)=\ddot q_0, \qquad \ddot q(t_f)=\ddot q_f.
\]

This should be the default method because it provides smooth point-to-point motion while remaining straightforward to derive and teach.

### Boundary-condition semantics

Boundary-condition arguments should follow the capabilities of the selected interpolation method rather than being silently ignored.

Preliminary behavior:

- `linear`: only endpoint coordinates are meaningful; derivative boundary-condition arguments should be rejected if explicitly supplied;
- `cubic`: endpoint velocities are supported, with omitted values interpreted as zero; acceleration boundary conditions are not supported;
- `quintic`: endpoint velocities and accelerations are supported, with omitted values interpreted as zero.

The exact validation messages and whether unsupported arguments produce `ValueError` or another exception type are deferred to detailed design.

### Explicit time vector

Both public trajectory-generation functions should accept an explicit numerical time vector `t`.

The time samples must be strictly increasing and contain enough samples to define and evaluate the requested trajectory. The initial API will not generate a time grid internally from combinations such as `tf`, `duration`, or `samples`.

For example:

```python
t = np.linspace(0.0, 3.0, 100)
traj = joint_trajectory(q0, qf, t, method="quintic")
```

This design keeps time discretization under the user's control and makes the returned data directly reusable by plotting, visualization, inverse kinematics, and numerical analyses.

### `JointTrajectory`

`joint_trajectory()` should return a structured `JointTrajectory` object containing at least:

- `t`;
- `q`;
- `qd`;
- `qdd`.

The preferred public shape convention is:

```python
trajectory.t.shape   == (N,)
trajectory.q.shape   == (N, dof)
trajectory.qd.shape  == (N, dof)
trajectory.qdd.shape == (N, dof)
```

so that `trajectory.q[k]` directly represents the joint configuration at sample `k`.

This convention intentionally matches the time-major orientation selected for `DynamicsSolution`.

### `PositionTrajectory`

`position_trajectory()` should return a structured `PositionTrajectory` object containing at least:

- `t`;
- `p`;
- `v`;
- `a`.

Cartesian position data should use three components consistently:

```python
trajectory.p.shape == (N, 3)
trajectory.v.shape == (N, 3)
trajectory.a.shape == (N, 3)
```

Planar motion should therefore be represented as a three-dimensional Cartesian trajectory with one coordinate held constant rather than introducing a separate 2D data model.

### Independence from `Robot`

`joint_trajectory()` and `position_trajectory()` should not require a `Robot` instance.

They are mathematical trajectory-generation tools and should not automatically:

- inspect robot joint types;
- enforce joint limits;
- solve inverse kinematics;
- perform collision checking;
- perform dynamics simulation.

Keeping trajectory generation independent from the robot model reduces coupling and makes the interpolation tools reusable in teaching examples outside a complete robot model.

Robot-specific trajectory validation may be considered as a separate future capability.

### Relationship with inverse kinematics

Generation of a Cartesian position trajectory and conversion of that trajectory into joint configurations should remain two explicit operations.

For example:

```python
cart = position_trajectory(
    p0,
    pf,
    t,
    method="quintic",
)

ik = solve_position_trajectory(
    robot,
    cart.p,
    q0=q0,
)
```

This separation is pedagogically intentional. `position_trajectory()` defines a desired Cartesian trajectory, while `solve_position_trajectory()` solves the robot-specific inverse-kinematics problem along the requested positions.

The new trajectory module should therefore complement rather than replace the position-trajectory IK capability introduced in Moro 0.4.0.

### Path versus trajectory terminology

Documentation should distinguish between a geometric path and a trajectory.

A path specifies geometric points without necessarily assigning time, whereas a trajectory describes coordinates as functions of time. The initial 0.5.0 API focuses on time-parameterized trajectories and does not introduce a separate public `Path` abstraction.

### Relationship with visualization

The trajectory module should not depend directly on visualization.

The selected result shapes should nevertheless support direct reuse, conceptually:

```python
traj = joint_trajectory(...)
visualizer.animate(traj.q)
```

or, after Cartesian trajectory IK:

```python
cart = position_trajectory(...)
ik = solve_position_trajectory(robot, cart.p, q0=q0)
visualizer.animate(ik.q)
```

Whether visualizers later accept `JointTrajectory` objects directly is a separate design decision.

### Initial examples and tests

The feature should eventually include examples covering at least:

- linear joint interpolation;
- cubic joint interpolation with nonzero boundary velocities;
- quintic joint interpolation with position/velocity/acceleration boundary conditions;
- comparison of linear, cubic, and quintic profiles;
- Cartesian position interpolation in 3D;
- planar position trajectories represented in 3D;
- use of `PositionTrajectory.p` with `solve_position_trajectory()`;
- use of `JointTrajectory.q` with visualization.

Tests should cover endpoint conditions, derivative endpoint conditions, exact output shapes, strictly increasing time validation, list/array inputs, dimensional consistency, method-specific boundary-condition validation, and numerical agreement with known polynomial cases.

### Explicitly outside the initial 0.5.0 scope

The following capabilities are not part of the accepted initial trajectory-generation scope:

- multiple-waypoint trajectories;
- splines;
- segment blending;
- trapezoidal velocity profiles;
- jerk-limited or S-curve profiles;
- automatic duration calculation from velocity or acceleration constraints;
- joint synchronization based on physical limits;
- joint-limit enforcement;
- robot-aware trajectory validation;
- obstacle-aware or collision-aware planning;
- path planning;
- pose trajectories;
- orientation interpolation;
- quaternion SLERP;
- online trajectory generation;
- time-optimal trajectory generation.

These features may be evaluated in later releases after the point-to-point polynomial trajectory API is stable.

### Deferred detailed-design decisions

The following points are intentionally deferred until detailed design and implementation of `trajectory.py`:

- exact dataclass definitions and invariants for `JointTrajectory` and `PositionTrajectory`;
- exact accepted input containers and dtype coercion;
- whether scalar one-DOF trajectories should be accepted directly or normalized to one-component vectors;
- exact minimum number of time samples;
- exception types and messages;
- implementation strategy for polynomial coefficient generation;
- whether joint and Cartesian interpolation should share an internal generic polynomial helper;
- final naming of Cartesian derivative boundary-condition arguments;
- treatment of floating-point endpoint tolerances.
